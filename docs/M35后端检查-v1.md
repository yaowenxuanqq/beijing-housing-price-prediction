## 三、P0 缺陷（联调前必须修）

### P0-1 非法区名静默通过，且被当成「东城区」处理

**现象**：`POST /predict/` 传 `district_name="火星区"`，返回 **200 + 一个看起来完全正常的预测结果**。

**根因**：类别列用 `OrdinalEncoder(handle_unknown="use_encoded_value", unknown_value=-1)`。未知类别被编码为 **-1**，而 `东城区` 是排序后的第一个类别，编码为 **0**。树模型的分裂条件 `district_name <= 0.5` 会把 -1 和 0 切到**同一侧**，于是未知区名被静默当成东城区。

实测编码与预测：

| district_name | 编码 | ratio |
|---|---|---|
| 朝阳区 | 6.0 | 1.0087 |
| 西城区 | 9.0 | 1.0649 |
| 海淀区 | 7.0 | 0.9140 |
| **东城区** | **0.0** | **0.8435** |
| **火星区** | **-1.0** | **0.8435** ← 与东城区完全相同 |
| **空字符串** | **-1.0** | **0.8435** ← 同上 |

**危害**：这是最危险的一类 bug——不报错、不返回异常值，用户拿到一个"合理"的数字，实际是错的。前端下拉框一旦传值有误，或用户手输区名，就会静默出错，且无人能察觉。答辩演示时也无法自证。

**修复**：在 serializer 加区名白名单校验。

`backend/apps/prediction/serializers.py` 顶部增加：

```python
_district_cache = None


def _valid_districts():
    """可用区域集合（首次调用时从库里读，之后缓存）"""
    global _district_cache
    if _district_cache is None:
        from apps.housing.models import House
        _district_cache = set(
            House.objects.values_list("district_name", flat=True).distinct())
    return _district_cache
```

在 `PredictRequestSerializer` 内增加：

```python
    def validate_district_name(self, value):
        valid = _valid_districts()
        if valid and value not in valid:
            raise serializers.ValidationError(
                f"未知区域：{value}，可选值为 {sorted(valid)}")
        return value
```

修复后 `火星区` 应返回 400 并列出 13 个可选区名。

### P0-2 相关性矩阵取样有严重时间偏倚，一个系数偏差 +0.25

**现象**：`/stats/correlation/` 用 `House.objects.values(*FIELDS)[:20000]` 取样，**没有 `order_by`**，实际取到的是物理存储顺序的前 2 万行。

实测这 2 万行的年份分布：

| 年份 | 接口取样 | 全量 |
|---|---|---|
| 2011 | 2,161 | 5,771 |
| 2012 | 9,497 | 37,021 |
| 2013 | 3,000 | 38,630 |
| 2014 | 1,209 | 32,553 |
| 2015 | 2,726 | 69,743 |
| 2016 | 1,330 | 90,791 |
| 2017 | 77 | 43,209 |
| **年份中位** | **2012** | **2015** |

样本严重偏向早期数据（2017 年只占 77 条）。

**后果**：相关性系数失真，且失真程度因特征而异。

| 特征对 | 接口取样 | 随机取样 | 全量 | 接口偏差 |
|---|---|---|---|---|
| community_average ~ unit_price | **0.9373** | 0.6897 | 0.6851 | **+0.2522** ❌ |
| house_age ~ square | -0.3245 | -0.3617 | -0.3603 | +0.0358 |
| community_average ~ square | -0.1150 | -0.1628 | -0.1469 | +0.0319 |
| square ~ unit_price | -0.1703 | -0.1761 | -0.1657 | -0.0047 |
| house_age ~ unit_price | 0.2998 | 0.3105 | 0.3078 | -0.0080 |
| rooms ~ unit_price | -0.0743 | -0.0759 | -0.0732 | -0.0011 |

`community_average ~ unit_price` 从全量的 0.685 被抬到 **0.937**，几乎变成"完全线性相关"。**这个数字如果进论文图表，是站不住的**——审稿人或答辩老师只要问一句"这 2 万行怎么取的"，就解释不清。

**修复**：改为随机取样。

`backend/apps/analysis/views.py` 第 60 行：

```python
# 原
qs = House.objects.values(*self.FIELDS)[:20000]
# 改为
qs = House.objects.order_by("?").values(*self.FIELDS)[:20000]
```

实测 `order_by("?")` 在 31.7 万行上耗时 **0.418s**（现状 0.082s），该接口非常调用，性能可接受。

改完后 `community_average ~ unit_price` 应回落到 ≈0.685。

## 四、P1 缺陷（建议修）

### P1-1 异常查询参数返回 500 错误页

`GET /houses/?min_price=abc` → **500**，返回 Django 调试 HTML 页。

根因在 `backend/apps/housing/views.py` 第 20–26 行：`float(p["min_price"])` 无异常捕获。`max_price`、`min_square`、`max_square` 同理。

演示时手改 URL 或前端传参有误就会崩成错误页，观感很差。

**修复**，在 `HouseListView` 内加辅助方法：

```python
    @staticmethod
    def _num(params, key):
        try:
            return float(params[key])
        except (TypeError, ValueError):
            return None
```

然后把 6 处筛选改为先取值再判断，例如：

```python
        v = self._num(p, "min_price")
        if v is not None:
            qs = qs.filter(total_price__gte=v)
```

### P1-2 响应内部轻微不自洽

返回 `ratio = 1.0851`，但 `1.0851 × 66421 = 72,073.4`，接口给的单价是 `72,071`，差 2.4 元/㎡。

原因是 `ratio` 被 `round(..., 4)` 而单价用的是未舍入的 `ratio`。占比 0.0034%，不影响使用，但严格说响应三字段不能互推。

**修复**：`backend/ml/predictor.py`，让 `ratio` 由单价反算：

```python
        unit_price = round(ratio * market, 0)
        ...
        return {
            "ratio": round(unit_price / market, 6),
            "predicted_unit_price": unit_price,
            ...
        }
```

## 六、做得出色的部分

1. **训练/推理共用同一份 preprocessing** —— `backend/ml/preprocessing.py` 的注释里写清了原因：Pipeline 被 joblib 序列化后记录的是模块路径，若 Transformer 定义在 `__main__` 里，Django 加载会失败。这个坑很多项目踩过，你提前规避了。

2. **特征对齐零误差** —— 线上构造的 17 个特征与离线全字段结果 `ratio` 差异为 **0.00000000**。我原本怀疑 `renovation`/`building_type` 存在 int/float 类型不匹配（训练列是 float 含 NaN，API 传 int），实测 6 个类别列 int 与 float 编码结果全部一致，虚惊一场。

3. **模型单例 + 503 兜底** —— `HousingPredictor.instance()` 用双检锁保证进程内只加载一次 92.7MB 模型；模型文件缺失时返回 503 并提示运行哪个脚本，而不是抛栈。

4. **`.gitignore` 分层处理得当** —— `db.sqlite3`、`data/models/`、`*.joblib` 全部忽略，同时用 `!data/metrics_v1.json` 等 5 条否定规则把实验指标纳入版本控制。这个"产物不入库、结论入库"的划分是对的。

5. **预测落库可追溯** —— 每次预测写入 `prediction_log`（含输入 JSON、ratio、model_version），实测 8 条记录完整。这在答辩时能直接展示"系统真的在用"。

6. **`np.clip(ratio, 0.05, 9.0)` 防外推** —— 与调参阶段的截断口径保持了一致，线上不会因为极端输入输出荒谬数字。
