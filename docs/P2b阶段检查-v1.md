## 二、P0：调参让部署模型变差了，这是本阶段的核心问题

调参目标选的是 `log1p(总价)`，而部署模型用的是 ES-3 的 ratio 口径，沿用了同一组参数。结果：

| RF（ES-3 部署口径） | R²_unit | 单价 MAE |
|---|---|---|
| 基线参数（当前部署） | **0.8523** | 6,715 元/㎡ |
| 沿用绝对价调出的参数（当前 tuned 产物） | **0.8388** | 7,032 元/㎡ |

**调优后反而降了 0.0135 R²、MAE 恶化 317 元/㎡。** XGBoost 调优后 0.8475 也未超过基线 RF 的 0.8523。也就是说，**P2b 目前对最终交付物的贡献是负的**——部署模型仍然只能用基线参数。

我按部署口径（ratio）实跑了一次同样的搜索（RF，n_iter=20，112 秒）：

| 配置 | R²_unit | 单价 MAE | 模型体积（压缩后） |
|---|---|---|---|
| 当前部署：基线参数（100 棵 / leaf=10） | 0.8523 | 6,715 | **50.6 MB** |
| **推荐**：ratio 调参（100 棵 / depth=25 / leaf=5） | **0.8603** | **6,542** | **90.9 MB** |
| ratio 调参（150 棵 / depth=25 / leaf=5） | 0.8608 | 6,531 | 136.2 MB |
| ratio 调参（200 棵 / depth=25 / leaf=5） | 0.8610 | 6,526 | 181.5 MB |
| ratio 调参最优（200 棵 / **depth=None** / leaf=5） | 0.8619 | 6,503 | 198.9 MB |
| 现状：沿用绝对价参数 | 0.8388 | 7,032 | 53.7 MB |

两点判断：

1. **按 ratio 调参是净收益**：相比现状的 0.8388，可拿回 **+0.023 R²、MAE 改善 490 元/㎡**；相比基线也有 +0.008。
2. **搜索给出的最优含 `max_depth=None`，不能直接用**——这正是当初导致 RF 模型 2.2 GB、Django 加载不了的元凶。建议把深度约束在 25，并优先选 **100 棵 / leaf=5**（90.9 MB），体积只比当前部署模型翻一倍，Django 侧完全可控。

**建议操作**：在 `04_tune.py` 增加 `--target ratio` 分支（或用 ratio 作为默认调参目标），重跑一次（RF 约 112 秒，四个模型合计约 7 分钟），产出取代现有 `tuned_*_es3.joblib`。
