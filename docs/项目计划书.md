## 一、项目概述与目标

### 1.1 项目概述

本项目以北京二手房市场为研究对象，基于 Kaggle 公开的北京链家二手房成交数据集（2011–2017 年，约 31.8 万条），设计并实现一个集数据可视化分析与房价预测于一体的 Web 系统。

系统采用 Django REST Framework 提供后端接口，Vue 3 + ECharts 构建前端界面，运用线性回归、决策树、随机森林、XGBoost 等多种机器学习模型进行房价预测，并通过 RMSE、MAE、R² 等指标完成模型对比与选型，最终实现面向用户的房价可视化分析与在线预测功能。

### 1.2 总体目标

完成一套可运行、可演示、可复现的房价预测与可视化分析系统，并形成完整的毕业论文与技术文档。

### 1.3 具体目标

1. 完成北京二手房数据的清洗与特征工程流程，形成规范化数据集。
2. 完成多模型训练、调优与对比实验，输出最优模型及完整评估结果。
3. 完成系统开发，实现数据管理、可视化分析、模型对比、房价预测四大核心功能。
4. 完成毕业论文一篇，并沉淀可复现的代码与文档。

## 三、技术方案与架构

### 3.1 技术栈

| 层次 | 技术选型 |
|---|---|
| 后端框架 | Django 5 + Django REST Framework |
| 后台管理 | Django Admin |
| 前端框架 | Vue 3 + Element Plus |
| 可视化 | ECharts |
| 数据库 | MySQL 8（开发期可用 SQLite） |
| 数据处理 | pandas + numpy |
| 机器学习 | scikit-learn + XGBoost |
| 地理处理 | GeoPandas / Shapely（行政区反查） |
| 开发工具 | VS Code / PyCharm |

### 3.2 分层架构

1. **表现层**：Vue 3 单页应用，负责图表展示与交互。
2. **接口层**：Django REST Framework 提供 RESTful API。
3. **业务层**：Django 各 app 实现数据管理、分析、预测等业务逻辑。
4. **数据层**：MySQL 存储清洗后的数据与预测记录。
5. **算法层**：离线训练脚本 + 在线推理服务。

### 3.3 关键设计原则

1. **训练离线、推理在线**：模型训练在独立脚本中完成，产出模型文件与指标文件；Django 启动时加载模型，接口只做推理。
2. **禁止请求内训练**：任何训练操作不得出现在请求处理路径中。
3. **防特征泄漏**：严格区分「预测时可得特征」与「成交后才知道的字段」。
4. **结果可复现**：固定随机种子，沉淀训练脚本与参数配置。

## 四、数据集说明与清洗策略

### 4.1 数据集概况

| 项目 | 内容 |
|---|---|
| 来源 | Kaggle 公开数据集（北京链家二手房成交数据） |
| 原始文件 | `data/new.csv`（GBK 编码，约 58.7 MB） |
| 规模 | 318,851 行 × 26 列 |
| 时间范围 | 2002-06 至 2018-01（主体为 2011–2017，约 31.8 万条） |
| 行政区 | 13 个区域编码 |

### 4.2 字段分组

| 分组 | 字段 |
|---|---|
| 标识类 | url、id、Cid |
| 空间类 | Lng、Lat、district |
| 时间类 | tradeTime、constructionTime |
| 交易过程类 | DOM、followers |
| 价格类 | totalPrice、price、communityAverage |
| 房屋属性类 | square、livingRoom、drawingRoom、kitchen、bathRoom、floor |
| 建筑属性类 | buildingType、buildingStructure、ladderRatio、renovationCondition、elevator |
| 权益与配套类 | fiveYearsProperty、subway |

### 4.3 数据质量问题与处理策略

| 问题 | 具体表现 | 处理策略 |
|---|---|---|
| 年份零散 | 2002–2010、2018 记录极少 | 过滤，仅保留 2011–2017 |
| 乱码值 | livingRoom 含 `#NAME?` | 该行剔除或修正 |
| 串列错位 | drawingRoom 混入 `中 6`、`中 16` 等楼层值 | 剔除异常行 |
| 类型错误 | bathRoom 混入 `2006` | 剔除异常行 |
| 极端值 | price 最小 1 元/㎡，totalPrice 最小 0.1 万，square 最大 1745 ㎡ | 分位数截断或物理阈值过滤 |
| 缺失值 | DOM 缺失约 15.8 万条；buildingType 缺 2021；elevator/subway/fiveYearsProperty 各缺 32 | DOM 直接删除；其余少量缺失按众数填充或删除 |
| 建造年份含「未知」 | constructionTime 有 9753 条「未知」 | 视为缺失，单独编码或按小区中位数填充 |

### 4.4 特征工程

1. **楼层解析**：`floor` 拆分为「楼层位置」（低/中/高/顶/底）与「总层数」两个字段。
2. **房龄构造**：`tradeTime 年份 − constructionTime` → `houseAge`。
3. **行政区还原**：以 Lng/Lat 与北京行政区划 GeoJSON 做点面判断，将 `district` 数字编码还原为区名。
4. **类别编码**：区名、装修、建筑类型、建筑结构等做独热编码或序数编码。
5. **数值标准化**：对面积、房龄、梯户比等做标准化处理。
6. **特征选择**：基于相关性分析与模型特征重要性筛选。

### 4.5 特征泄漏风险清单（重要）

| 字段 | 风险 | 处理 |
|---|---|---|
| price | 与 totalPrice 存在数学换算关系（price = totalPrice × 10000 / square） | 预测总价时必须排除 |
| totalPrice | 预测单价时同理排除 | 预测单价时必须排除 |
| communityAverage | 小区均价本身接近目标值，构成泄漏 | 默认排除，或仅在对照实验中测试 |
| DOM | 挂牌到成交天数，成交后才可得 | 从建模特征中排除 |
| followers | 成交后的关注热度，预测时不可得 | 从建模特征中排除 |
| url、id、Cid | 无泛化意义的标识 | 排除 |

## 六、算法方案与评估

### 6.1 目标变量策略

- **主目标**：`totalPrice`（总价，万元）——系统输出直观。
- **对照实验**：`price`（单价，元/㎡）——消除面积主导效应，体现建模深度。
- 两者互为换算关系，建模时必须互斥，不得同时作为特征。

### 6.2 模型集合

| 模型 | 定位 |
|---|---|
| 线性回归 | 基线模型 |
| 决策树 | 非线性对照 |
| 随机森林 | 集成方法，稳健 |
| XGBoost | 梯度提升，预期最优 |

### 6.3 训练流程

1. 划分训练集与测试集（固定随机种子）。
2. 特征工程与预处理（编码、标准化）。
3. 各模型基础训练。
4. 5 折交叉验证 + GridSearchCV 超参数调优。
5. 测试集评估与结果对比。
6. 选定最优模型，序列化为 `model.pkl` 并导出指标 JSON。

### 6.4 评估指标

| 指标 | 含义 | 方向 |
|---|---|---|
| RMSE | 均方根误差 | 越小越好 |
| MAE | 平均绝对误差 | 越小越好 |
| R² | 决定系数 | 越接近 1 越好 |

### 6.5 模型选型原则

以测试集表现为准，综合 RMSE 与 R²；若差异不显著，优先选择结构更简单、推理更快、可解释性更强的模型。

## 八、风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 数据时效性受质疑 | 影响选题合理性 | 明确定位为「基于特征的房价评估」，并保留补充新数据的后手 |

| Django 学习曲线 | 拖慢开发进度 | 先跑通最小可运行 Demo，再逐模块扩展 |
| 开发与论文时间冲突 | 影响定稿 | 按里程碑推进，系统开发尽量在寒假前完成主体 |
| 数据清洗规则主观 | 影响可复现性 | 清洗规则脚本化、参数化，并记录在文档中 |
| 大文件误入仓库 | 仓库膨胀 | 配置 `.gitignore`，排除 CSV 与模型文件 |
