## 总体判断

这份计划书的质量在同类本科毕设中属上游：**4.5 节特征泄漏清单、12.2 节特征列冻结、12.6 节验收清单**这三处是真正的工程意识，很多硕士项目都做不到。第十一、十二章的同类项目调研与借鉴落地也不是凑字数。

但它现在还不能照着开工。卡住的不是细节，是两个会在中期检查前爆掉的硬伤：**数据集划分口径错误**和**调参没有时间预算**。前者会让您的模型指标失去意义（答辩一问就露馅），后者会让 M3 里程碑（2026.11 完成五模型训练对比）根本跑不完。

## 一、阻塞级（P0）—— 不改就翻车

### P0-1 数据集划分口径错误，指标必然虚高

**位置**：6.7 节「实验设置与可复现性」——「数据划分：训练集 : 测试集 = 8 : 2，**随机打乱**」；「交叉验证：5 折交叉验证」

**现状**：明确写了随机打乱 + 普通 K 折交叉验证。

**风险**：本数据集跨 2011–2017 共 7 年，北京房价在此期间从约 2 万/㎡ 涨到 6 万+/㎡，存在强时间趋势。随机划分会让训练集混入 2017 年样本、测试集混入 2012 年样本，**模型等于看到了未来**，R² 会虚高到 0.9 以上。这恰恰和您在 4.5 节拼命做泄漏治理的初衷自相矛盾——费劲排除了字段级泄漏，却在划分层面漏了一个更大的。答辩老师只要问一句「你的测试集和训练集时间上是怎么切的」，这个数字就站不住。

同理，普通 `KFold` 在时序数据上也不成立，必须用 `TimeSeriesSplit`。

**建议替换文本**（替换 6.7 节对应两行）：

| 项目 | 设置 |
|---|---|
| 数据划分 | **时序划分**：2011-01 至 2016-06 为训练集，2016-07 至 2017-12 为测试集（约 8:2）。禁止随机打乱 |
| 交叉验证 | 训练集内部使用 `TimeSeriesSplit(n_splits=5)`，禁止普通 `KFold` |
| 补充对照 | 另做一组随机划分实验，仅用于量化「时序划分 vs 随机划分」的指标差异，在论文中作为方法严谨性的证据 |

> 采用时序划分后 R² 大概率会下降，这是**正确的结果**，不是失败。把它写成论文里的一个发现：「随机划分会高估模型性能约 X 个百分点」，反而是一个加分的方法论点。

### P0-2 调参无时间预算，M3 里程碑必然延期

**位置**：6.6 节超参数搜索空间、6.7 节、第八节风险表

**现状**：给出了五模型的候选网格，仅在表下加了一句「搜索空间过大时改用 RandomizedSearchCV（n_iter=50）」。没有硬件章节，没有组合数上限，没有单次训练时长约束。

**风险**：我按 6.6 的网格算了组合数：

| 模型 | 候选组合数 | × 5 折 | 说明 |
|---|---|---|---|
| 决策树 | 5×4×3 = 60 | 300 | 可接受 |
| 随机森林 | 3×3×3×3 = 81 | 405 | 300 棵树 × 25 万样本，单次约 20s → 约 2.3 小时 |
| **XGBoost** | 3×3×3×3×3×3 = **729** | **3,645** | 平均 600 棵树 × 25 万样本，单次 60–180s → **约 60–180 小时** |
| MLPRegressor | 3×3×2 = 18 | 90 | 25 万样本上单次可达数分钟 → 数小时 |

合计约 **4,440 次训练**。您的机器是 Core Ultra 5 225U（U 系列低功耗，无独显）+ 16GB 单通道内存，**纯训练耗时保守估计 60 小时以上**，还不算特征工程、失败重跑、以及 6.7 节要求的「3 个随机种子重复实验」（若误用于调参阶段则再 ×3）。

而 M3 里程碑要求 **2026.11 中期检查前完成特征工程 + 五模型训练对比**。按现状这个交付物出不来。

**建议替换文本**（新增 6.6 节表后说明，并新增「6.8 硬件约束与调参预算」一节）：

```
### 6.6 补充约束

调参阶段统一使用 RandomizedSearchCV，n_iter 上限 30；
调参在 5 万条随机子样本上进行，最终模型再用全量训练集训练一次。
单次训练时长上限 120 秒，超时则缩减网格重跑。

### 6.8 硬件约束与调参预算（新增）

| 项目 | 约束 |
|---|---|
| 开发机 | Core Ultra 5 225U / 16GB 单通道 / 无独显 / 非管理员权限 |
| 单模型调参预算 | 随机森林 ≤ 1 小时；XGBoost ≤ 2 小时；决策树、MLP ≤ 30 分钟 |
| 调参总预算 | ≤ 5 小时 |
| 组合数上限 | 单模型 ≤ 30（RandomizedSearchCV n_iter=30） |
| 调参数据规模 | 5 万条子样本 |
| 稳定性验证 | 仅对最终选定的 1 个模型做 3 种子重复，不用于调参阶段 |
| 超时降级 | 预算用尽即取当前最优参数，记录为「未充分调参」并在论文中说明 |
```

**同时必须在第八节风险表补一行**（现风险表漏了这条最可能发生的风险）：

| 风险 | 影响 | 应对措施 |
|---|---|---|
| **训练耗时超预期** | 中期检查前无法产出模型对比结果 | 调参用子采样 + RandomizedSearchCV；设置单模型时长上限；预留「未充分调参」降级方案；优先保证五模型基线对比完成，调优作为增量 |

## 二、重要级（P1）—— 决定成败

### P1-1 地铁站坐标数据源缺失，`dist_to_subway` 无米下锅

**位置**：4.4 第 6 条、12.2 节 L8、开题报告 3.2 特征工程

**现状**：三处均承诺「距最近地铁站距离（站点坐标 + KDTree 最近邻）」，但**全文未说明北京地铁站坐标从哪来**。

**风险**：这是开题报告里已经写出去的承诺，数据源没着落就会在中期检查时卡住。要么爬取（有法律与维护成本），要么手工整理（北京约 400+ 站点，工作量不小）。

**建议**：数据集中已有 `subway` 字段（是否近地铁，0/1），它本身就是地铁可达性的有效表征。建议把优先级调整为：

| 方案 | 成本 | 推荐度 |
|---|---|---|
| **A. 优先用现有 `subway` 布尔字段**，距离特征降为选做 | 零成本 | ★★★ 推荐 |
| B. 补一份地铁站坐标 CSV（公开数据手工整理），实现距离特征 | 中等 | ★★ |
| C. 直接砍掉距离特征 | 零成本 | ★（会使开题承诺未兑现） |

若采用 A，开题报告中的表述需相应调整为「以 subway 布尔特征为主，距离特征视数据获取情况补充」。

### P1-4 `house_age` 未定义边界，可能出现负值

**位置**：4.4 第 2 条「房龄构造：tradeTime 年份 − constructionTime」

**现状**：未定义异常值处理。

**风险**：`constructionTime` 实测有 **19,283 条「未知」（6.05%）**，而非文档所写的 9,753 条（**项目计划书 4.3 与开题报告 3.2 都写的 9,753，两处均需订正**）。填充后必然出现 `house_age` 为负或异常大的情况，直接进模型会污染结果。

**建议**：补规则——`house_age` 取值限制在 [0, 70]，小于 0 视为缺失并按同小区中位数填充，大于 70 截断至 70。同时把 9,753 订正为 19,283。

### P1-6 GeoPandas 行政区反查属过度设计，且有合规与安装风险

**位置**：4.4 第 3 条、3.1 技术栈「GeoPandas / Shapely」

**现状**：计划用 Lng/Lat 与北京行政区划 GeoJSON 做点面判断，把 district 数字编码还原为区名。

**风险**：三重风险叠加——
1. **安装风险**：GeoPandas 依赖 GDAL，Windows 非管理员权限下安装常失败；
2. **合规风险**：行政区划 GeoJSON 必须来自权威源（自然资源部标准地图服务），随意爬取边界数据有合规问题；
3. **过度设计**：`district` 字段**已经是 1–13 的行政区划编码**，只有 13 个取值，根本不需要几何计算。人工核对一次即可得出映射表。

**建议**：降级为「13 个编码 → 区名映射表」，写入 `scripts/config/district_mapping.py`，彻底移除 GeoPandas/Shapely 依赖。核对方法：取每个编码的 Lng/Lat 中位数，对照公开行政区划位置人工确认，半小时内可完成。

> 注意：开题报告 3.3「拟解决的关键问题」第 3 条写的是「如何在缺少编码映射表的情况下还原北京行政区名称」。改用映射表后这个问题自然消解，答辩时如实说明「经评估，13 个编码可通过人工核对建立映射表，无需几何计算」即可，属于**合理简化**，不算未兑现承诺。
